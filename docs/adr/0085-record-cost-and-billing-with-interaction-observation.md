# 随请求观测写入成本与计费，接受过载时丢失

Stravia 需要把每次模型调用的按量成本与计费金额长期计入用量统计，并维护 API Key 的已消费，供消费上限在准入时判定。我们选择让这些金额随现有的请求观测事件写入：Target 尝试结束或用量补报时，金额与用量在同一个观测事务内落库，由数据库触发器同时累加到用量统计桶和该 API Key 的已消费累计行；准入只读取累计行，不产生写入。这样不为每次模型调用增加独立的写事务，也让计费与 Token 用量始终出自同一份事实。

代价是观测事件经有界队列 `try_send` 投递，过载时会被丢弃并只留下观测缺口；被丢弃事件对应的成本与计费随之丢失，不会补记。异步写入的延迟也让已消费略滞后于实际调用，消费上限因此可能被在途请求和未落库的金额小幅超出。计费因此是用于消费上限的内部记账，不是可对外结算的账单。

## Considered Options

- 计费单独走不可丢弃的写入路径，每次模型调用一个独立的小事务：数据可靠，但 SQLite 单写者下每次调用都要多拿一次写锁，与观测写入争用。
- 观测通道对计费相关事件改为阻塞发送：数据库变慢时背压会传到请求路径，拖慢推理交付。
- 只在进程内存中维护已消费：重启丢失，多实例之间不一致。

## Consequences

- 计费金额一经落库即不再改变；价格、汇率或计费设置的后续修改只影响之后的调用。
- 每次 Target 尝试至多确认一次用量，且不晚于尝试结束，因此金额在尝试结束时一次算定，随结束事件写入。
- 清零已消费只重置累计行并记录清零时间，不删除或改写任何计费明细与统计桶。
- 如果以后需要可对外结算的计费，需要重新评估本决策，改用可靠写入路径。
